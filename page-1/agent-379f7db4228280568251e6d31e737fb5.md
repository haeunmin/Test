## 2. 셀렉이의 탄생

* 최근 기업들은 생성형 AI와 대규모 언어 모델을 활용하여 사내 업무 전반의 디지털 전환을 가속화하고 있다.
* 특히 사내 문서 검색, 회의록 및 보고서 작성, 데이터 요약, 개발 지원 등 반복적이고 시간이 많이 소요되는 업무를 AI로 지원하려는 시도가 확대되고 있다.
* 이에 따라 여러 기업에서 사내 챗봇, 지식 검색 시스템, 문서 작성 도구 등을 도입하며 AX(AI Transformation)를 추진하고 있다.

마침 사내에는 자체 개발 중인 AI 평가 플랫폼 다투모가 있었고, 다투모 역시 실제로 돌아가는 사내 에이전트를 필요로 하던 참이어서 셀렉이가 그 역할을 맡아보기로 했다.

## 3. 이걸 가능하게 하는 셀렉이의 구조

* 셀렉이는 다양한 사용자 인터페이스에서 전달된 요청을 하나의 Agent API를 통해 처리하고, 요청의 복잡도와 목적에 따라 멀티 에이전트 워크플로 또는 개별 전문 에이전트를 실행하는 구조로 설계되었다.
* 전체 시스템은 크게 **Adapter Layer**, **Agent API Layer**, **Multi-Agent Workflow**, **Specialist Agent Runtime**, **Shared Runtime Resources**의 다섯 영역으로 구성된다.

### 3.1 셀렉이 구성

#### 3.1.1 멀티 에이전트 구조

* 셀렉이는 사용자의 요청을 분석하고, 요청에 적합한 기능을 선택하여 업무를 수행하는 멀티에이전트 시스템 기반이다.
* 하나의 언어 모델이 모든 업무를 직접 처리하는 방식이 아니라, 업무 계획 수립, 도구 선택, 정보 검색, 데이터 조회, 결과 검토 및 답변 생성 등의 역할을 여러 구성요소가 분담하도록 설계하였다.
* 사용자가 자연어로 질문이나 업무를 요청하면, 셀렉이는 먼저 요청의 목적과 필요한 작업을 분석한다. 이후 요청을 처리하기에 적합한 전문 Agent를 선택하고, 사내 문서(Notion), Slack, 데이터베이스 등 필요한 데이터 소스에 접근하여 정보를 수집한다.
*   셀렉이의 전체 처리과정은 다음과 같다.

    **사용자 요청 → 요청 분석 및 작업 계획 → 전문 Agent 선택 → 데이터 및 도구 활용 → 결과 통합 → 최종 답변 생성**
* 셀렉이의 전체 시스템은 크게 **Adapter Layer**, **Agent API Layer**, **Multi-Agent Workflow**, **Specialist Agent Runtime**, **Shared Runtime Resources**의 다섯 영역으로 구성된다. 각 영역은 사용자 요청 수신, 실행 방식 결정, 전문 작업 수행, 결과 통합, 공통 자원 제공 등의 역할을 분담한다.

**Adapter Layer**

* Adapter Layer는 사용자 또는 외부 시스템이 셀렉이에 접근할 수 있도록 지원하는 인터페이스 계층이다. 현재 셀렉이는 Slack Bot, CLI Client, HTTP Caller를 통해 요청을 전달받을 수 있다.
* Slack Bot은 전사원들이 Slack 대화창에서 자연어로 셀렉이의 기능을 사용할 수 있도록 지원한다. 사용자는 Slack에서 문서 검색, 정보 조회, 외부 자료 탐색 및 업무 자동화 요청을 수행할 수 있다.

### 3.2 셀렉이 에이전트 시스템 구조

#### 3.2.1 멀티에이전트 구성

> 셀렉이는 사용자의 요청을 분석하고, 요청을 수행하기 위한 작업을 계획한 뒤, 각 작업에 적합한 전문 에이전트를 실행하여 최종 결과를 생성하는 멀티 에이전트 기반 시스템이다.

* 셀렉이의 에이전트 시스템은 크게 **전체 실행 과정을 조정하는 상위 구성요소**와 **실제 업무를 수행하는 전문 에이전트**로 구성된다.
* **상위 구성요소는** 사용자 요청을 수신하고, 작업을 분해하며, 적절한 전문 에이전트를 선택하고, 각 에이전트의 결과를 검토·통합한다.
* **전문 에이전트는** Slack 검색, Notion 문서 조회, 웹 검색, 웹페이지 수집, 텍스트 처리 등 특정 업무를 담당한다.
* 이와 같은 역할 분담을 통해 단순한 정보 조회뿐만 아니라 여러 데이터 소스와 작업이 결합된 복합적인 요청도 단계적으로 처리할 수 있다.

#### 3.2.2 서브 에이전트 구성 및 DB

*   **HR FAQ**

    사내 인사팀 FAQ 지식베이스(FAISS)를 검색해서 인사·총무·근태·장비·복지 질문에 답하는 RAG 에이전트
*   **NOTION READ**

    사내 Notion을 읽기 전용으로 뒤져서 근거(본문·DB row)를 찾아오는 에이전트
*   **SLACK**

    사내 Slack 대화를 검색해서 "누가 언제 어디서 뭐라고 했는지" 근거를 모아오는 읽기 전용 에이전트
*   **SCHEDULER**

    "매주 월요일 9시에 주간보고 정리해줘" 같은 걸 등록해두고, 시간 되면 실제로 어시스턴트를 다시 돌려서 결과를 채널에 쏴주는 에이전트
*   **PARSER**

    PDF에서 텍스트 뽑아서 검색 가능한 형태로 구조화하는 에이전트
*   **REPORTER**

    팀 보고서 양식을 등록해두고, 그 양식의 빈칸을 채팅으로 채워서 Notion에 붙여넣을 마크업으로 뽑아주는 에이전트
*   **TEXT**

    도구가 하나도 없는 순수 변환 워커
*   **DB 구조**

    셀렉이의 모든 기록은 **하나의 ledger (원장) 데이터베이스**에 남는다. 누가 어디서 무엇을 물었고, 어떤 계획으로 어떤 도구를 불러 답했으며, 그 답에 어떤 반응이 달렸을지를 단계별로 나누어 저장한다.

    * 기록은 **사람 → 대화 → 질문 → 실행 → 단계 → 도구 호출**의 순서로 세분화되며, 각 단계는 이전 단계와 1:N 관계를 이룬다.
    * **한 사람이 여러 대화를 열고**, 한 대화에 여러 질문이 오가며, 한 질문은 한 번의 실행을 유발하고, 한 실행은 여러 단계로 나뉘며, 한 단계는 여러 도구를 호출한다.
      * **질문한 사람은 대화가 아니라 질문에 기록된다.** DM은 사용자와 1:1로 대응하지만 채널 스레드에는 여러 사용자가 함께 질문하므로, 발화자는 대화(session)가 아닌 질문(turn)의 속성이다.
      * **실행 기록은 운영 기록과 하드 FK로 묶지 않는다.** 실행 기록은 재수 및 재생성 될 수 있는 반면 운영 기록은 보존되어야 하기 때문이다.

### 3.2 주요 구성 모델

*   **LLM**

    셀렉이의 모든 에이전트는 **하나의 LLM 클라이언트**를 공유한다. 어떤 모델을 쓸지는 코드가 아니라 환경변수 한 줄이 정하며, 에이전트는 자기가 어떤 모델 위에서 돌고있는지 알지 못한다.

    * 현재 `gpt-5.4` (OpenAI Responses API, reasoning effort `low`)를 사용한다.
    * 공급자는 openai / anthropic / openai\_compatible 세 갈래로 갈아끼울 수 있다. `anthropic`은 `claude-opus-4-7`로, `openai_compatible`은 Ollama / LiteLLM / vLLM 같은 OpenAI 호환 게이트웨이로 붙는다.
*   **MCP 툴**

    외부 시스템(Notion / Slack)에 닿는 도구는 전부 **MCP 서버를 통해서만 노출**된다. 에이전트가 직접 API를 치지 않고, MCP 서버가 한 겹 앞에 서서 무엇을 부를 수 있는지 자체를 통제한다.

    * 도구는 서버에서 발견(discover) → 화이트리스트 필터 → LLM 에 노출 순서로 걸러지며, 걸러진 도구는 모델의 도구 목록에 아예 오르지 않는다.
    * **Notion**은 공식 서버(`@notionhq/notion-mcp-server`)를 stdio로 띄우되, 읽기 전용으로 잘라서 쓴다. read-only 13종만 통과시키고 create / patch / update / delete / move / comment 계열은 전부 차단해, 봇이 사용자 대신 페이지를 만들거나 고칠 수 없다. 여기에 결정적 로컬 도구 6종(`parse_notion_url` · `find_db_by_name` · `resolve_notion_target` · `inspect_db_schema` · `fetch_page_full` · `query_inline_db_rows`)을 얹는다.
    * **Slack**은 공식 서버 대신 FastMCP로 직접 구현했다(`agent.agents.slack.server`). 노출하는 도구는 4종이며 전부 조회 전용이고, 권한 경계를 따라 갈려 있다 — `slack_search_context` / `slack_find_threads`는 봇이 참여하지 않은 공개 채널까지 워크스페이스 전체를 검색하고(Real-time Search API), `slack_search_mentions` / `slack_read_thread`는 봇이 멤버인 채널에서만 동작한다.
*   **검색 및 임베딩**

    사내 지식베이스는 **로컬 FAISS 인덱스**에 벡터화해 둔다. 검색 전략은 질의 성격에 따라 `RETRIEVER_STRATEGY`로 갈아끼울 수 있다.

    * auto(OpenAI `text-embedding-3-small` 임베딩 + FAISS 벡터 검색)가 기본이며, 정확한 코드·고유명사에는 임베딩 비용이 없는 bm25 키워드 검색이, 품질이 가장 중요하면 둘을 RRF로 융합하는 hybrid가 낫다.

## 4. 그런데, 셀렉이는 정말 잘하고 있을까?

### 4.1 다투모 시연

> 셀렉이는 2026년 6월 1일 첫 커밋 이후 약 2개월간 개발되어, Slack, HTTP API, CLI 세 입구가 같은 실행 코어를 호출하는 구조 위에 여러 전문 에이전트를 갖춘 상태에서 2026년 7월 15일에 셀렉이를 다투모에 연결해 자체평가의 메트릭을 그대로 재현해보는 평가 시연이 진행되었다.

* 시연의 목적은 셀렉이의 성능 확인이 아닌, 셀렉이를 다투모에 연결해 자체평가를 그대로 재현해서 돌려 직접 수행한 결과와 비교하는 것이었다.
  * 클라이언트의 관점, 특히 "비전문가"의 관점에서 바라보는 다투모의 사용성을 직접 경험해보기 위한 작업이었다.
* retriever 모듈과 tool use 모듈 두 갈래로 평가를 실행하였고, 그 과정에서 10여 개의 문제 영역이 도출되었다.
  * 셀렉이는 다투모의 첫 내부 클라이언트 케이스로 쓰였다. 평가 대상인 동시에, 평가 플랫폼의 사용성을 검증하는 도구이기도 했다.

### 4.2 실사용 평가의 부재

시연을 거쳤음에도 셀렉이의 실사용 평가는 여전히 확보되지 않았다.

1. **평가할 실사용 데이터가 없다.** 셀렉이가 사내에 배포되어 사용돼보지 못했기 때문에 아직 실제 사용자가 업무 맥락에서 던진 질문이 존재하지 않는다.
2. **준비한 다투모 플랫폼 기반의 평가마저 완주되지 못했다.** 다투모 시연에서 계획했던 hr\_faq 서브에이전트의 전체 평가는 구성되지 못하고 Retriever 평가로 범위가 축소되었으며, 실행한 평가도 메트릭 계산 단계에서 INTERNAL\_SERVER\_ERROR로 전부 실패했다. 이어서 진행한 tool use 평가는 툴 사용에 대한 gold set의 부재로 인해 제대로 된 평가가 진행되지 못했다.
   * 평가 결과가 나오지 못했기 때문에 아직 셀렉이가 잘하는지 못하는지 아무도 알 수 없다. 시연을 통해 얻으려고 했던 것은 "다투모가 셀렉이를 평가할 수 있는가"였고, 그 답이 긍정적이지 못했기 때문에 셀렉이의 능력치에 대한 평가는 아직 하지 못했다.
   * 정답셋은 만든 사람의 상상력 이상으로 구성될 수 없다. 설령 평가가 제대로 돌아간다 하여도, 개발자가 떠올린 질문은 이미 대비가 된 질문이므로 실패는 예상 밖의 질문에서 드러난다.

실사용 데이터를 수집하여 평가를 실행해보아야 한다.

### 4.3 실사용 환경: 평가의 전제조건

* **의도 분포:** 사람들이 실제로 무엇을 묻는지에 대한 분포를 알아야 플래너의 라우팅 설계에 대한 평가가 제대로 이루어질 수 있다.
* **표현의 다양성:** "전에 물어본 그거", "저번 그 문제"같이 지시대명사를 사용한 요청은 실제 대화에서만 나오며, 실사용 데이터를 기반으로 해야 사용 환경을 더 정확하게 구현해 평가를 진행할 수 있다.
* **동시성:** 여러 사람이 같은 스레드에 동시에 요청하는 상황처럼 서로 다른 쿼리가 겹칠 때의 사용성을 직접 확인할 수 있다.
* **시간 축:** 예약의 정시 발화, 재시작 복구, 백오프 재시도, dead-letter 통지는 시간이 실제로 흘러야 검증된다.
* **권한 경계**는 실제 워크스페이스에서만 드러난다. 봇이 어느 채널에 초대되어 있고 어느 페이지에 접근 권한이 있는지는 조직의 실제 상태이지, 테스트로 만들 수 있는 조건이 아니다.
* **만족도**는 대리 지표로 대체할 수 없다. 검색 정확도가 높아도 답이 쓸모없을 수 있으며, 그 판단은 요청한 사람만 내릴 수 있다. 이미 구축되어 있는 이모지 반응 수집 기능으로 이를 수집할 수 있다.
* **평가 데이터의 보안** 부담도 실사용이 해소한다. 시연에서는 사내 DB·내부 문서를 평가 플랫폼에 직접 올려야 하는 구조가 부담으로 지적되었으나, 실사용 로그는 이미 우리 원장 안에 있다.

결과적으로 실사용 환경에서의 로그가 평가 데이터와 평가 골드셋 둘 다 구축하는 기반이 될 수 있다.

### 4.4 셀렉이를 통한 평가 발전을 위한 접근

평가를 하는 입장에서 놓치는 부분이 없을 수가 없고, 클라이언트가 요구하는 것을 다 구현해보기 어려운 점 때문에 셀렉이를 통해 "블루팀·레드팀"처럼 에이전트 개발팀과 평가팀으로 나누어 평가의 방향성을 분명히 하고 더 "잘" 하고자 한다.

* 클라이언트 입장에서는 무엇을 다음에 고쳐야 하는지, 현재 개발 중인 에이전트가 어느 정도인지 알 수 없기 때문에 어떻게 발전시키며 언제 배포해야 할지에 대한 고민을 가지고 평가를 요구한다.
  * 실제 사용 사례가 확보되면 tool use나 라우팅 같은 설계적 측면에서 근거를 기반으로 능력치를 판단할 수 있다.
* 평가팀은 클라이언트가 위처럼 요구하는 사항을 평가할 personalized 된 데이터가 부족하다. AX 플랫폼 평가를 요구하는 사람 입장에서 줄 수 없는 데이터를 직접 제공해줄 기반이 없으며, 그걸 이용한 평가를 어떻게 발전시킬지에 대한 로드맵도 부재하다.
  * 셀렉이의 실사용 로그를 통해 generalized된 AX 기반 데이터를 얻을 수 있으며, 그것에 기반해 클라이언트가 요구하는 평가를 제공해줄 밑바탕을 닦을 수 있다.

결국 평가는 고객의 만족이 우선시되어야 한다. 그러므로 셀렉이의 배포 및 실사용을 다투모 플랫폼과 셀렉트스타 평가의 첫 번째 고객으로 삼아 회사의 상품을 발전시키려는 목적을 가지고 있다.

## 5. 왜 지금 배포해야 하는가?

배포의 일차 목적은 기능 제공이 아니라 데이터와 평가 대상의 확보다. 셀렉이의 원장은 사람 → 대화 → 질문 → 실행 → 단계 → 도구 호출을 이미 단계별로 기록하고 있으므로, 사용이 시작되는 순간부터 평가 자산이 자동으로 쌓이는 구조이다.

* 실제 사용 분포가 확보되면 라우팅, 프롬프트, 도구 설계를 근거를 기반으로 평가하고 발전시킬 수 있다.
* 단계별 실행 기록이 쌓이면 어느 에이전트에 실패가 집중되는지, 재시도가 어디서 발생하는지 정량적으로 확인할 수 있다.
* 사용자들의 이모지 반응이 쌓이면 만족도와 답변을 묶어서 라벨링할 수 있다.
  * 벤치마크 데이터 준비 부담을 줄일 수 있다. 다투모 시연에서도 가장 큰 어려움 중 하나가 "쓸 수 있는 벤치마크가 없어 직접 만들어야 한다"는 것이었는데, 실사용 로그 자체가 데이터셋의 기반이 될 수 있다.

현재 셀렉이로 보는 AX 개발자 입장에서의 병목은 기능 부족이 아니라 근거 부족이다. 무엇을 다음에 고쳐야 하는지 판단할 자료가 없다는 점이 가장 큰 제약이며, 이전 다투모 시연은 그 자료를 만들어내지 못했다.

* 지금 상태로 개발을 더 진행하면 검증되지 않은 가정 위에 기능이 쌓인다. 12종의 에이전트 중 9종은 평가 기준조차 없고, 나머지 3종도 평가가 완주되지 않았다.
* 셀렉이 배포는 다투모 개선의 조건이기도 하다. 이번 시연에서 드러난 "멀티에이전트를 어느 모듈 단위로 평가할 것인가"라는 문제는 실제로 돌아가는 멀티에이전트가 있어야 답할 수 있다. 셀렉이가 사내에서 운영되면, 다투모는 살아 있는 레퍼런스 케이스를 갖게 된다.
  * 실행 기록은 운영 기록과 하드 FK로 묶여 있지 않으므로, 재실행·재생성이 자유롭다. 평가 목적의 반복 실험이 운영 데이터를 훼손하지 않는다는 뜻이며, 이는 배포 후 개선 사이클을 빠르게 돌릴 수 있는 구조적 근거다.
  * 에이전트 평가는 결국 사용성의 발전에 목적을 두는 경우가 많다. 쓰이지 않는 시스템은 평가될 수 없고, 평가되지 않는 시스템은 좋아지지 않는다.

## 6. 결론

이번 다투모 시연을 통해 확인된 것은 다투모 자체의 사용성이었고, 셀렉이에 대한 평가는 여전히 미완의 상태로 남아있다. 정답셋 구성, 실사용 질문 분포, 실사용 환경의 여러 조건들이 아직 갖춰지지 않았다는 점을 고려하면, 평가가 완주되지 못한 것도 어느 정도 자연스러운 결과로 보인다.

* 현재로서는 평가할 대상에 대한 근거 자체가 부족한 상황으로 판단된다. 무엇을 기준으로, 어떤 데이터로 평가해야 하는지에 대한 밑그림이 아직 충분히 그려지지 않은 것으로 보인다.
* 평가 기준이 마련되지 않은 에이전트가 다수 존재하는 상태에서는, 향후 평가를 어떤 방식으로 발전시켜 나갈지에 대한 고민이 계속 필요할 것으로 보인다.
* 실사용을 통해 축적되는 기록들이 평가 데이터와 골드셋의 기반이 될 수 있다는 점은, 앞으로의 평가 설계에 참고할 만한 방향으로 여겨진다.

종합적으로 볼 때, 셀렉이에 대한 평가를 어떻게 구체화하고 발전시켜 나갈지는 여전히 열려있는 과제로 남아있으며, 이에 대한 추가적인 논의와 검토가 필요해 보인다.
